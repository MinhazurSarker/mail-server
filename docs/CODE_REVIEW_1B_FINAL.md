## Remaining defects and corrections

1. **P1 — Activation is still non-atomic; losing onboarding overwrites the winner's factor (R3, new regression).** Moving consumption first makes a later write failure unretryable with that ticket. More seriously, two different valid onboarding tickets can both read the user as pending and consume independently. A completes activation; B then upserts its different secret at [AuthService:483–493](../packages/service/src/services/AuthService.ts#L483), and only afterward loses the pending→active update at line 513. The activated account retains **B's secret despite B receiving an error**. The added unique index prevents duplicate rows, not replacement of the winner's row. Real MongoDB checks reproduced both cases using controlled scheduling/failure hooks. Commit consumption, enrollment, and version-bound activation together, or implement an idempotent, recoverable state machine with one user-level owner. Test failures after each write and two different onboarding tickets/secrets.

2. **P1 — Revocation can be bypassed by an in-flight old ticket (R5).** Reproduction: claim/validate generation 1; revocation writes user generation 2 and pauses before ticket invalidation; verification reloads generation 2 at [AuthService:330](../packages/service/src/services/AuthService.ts#L330), consumes the still-pending ticket, and signs generation 2 at line 385; revocation finishes and cannot invalidate that consumed ticket/token. Bind completion and minted token generation to the password proof's generation; coordinate revocation and commit. Add a barrier at this exact boundary, not only sequential revoke-then-claim coverage.

3. **P1 — No migration establishes the new uniqueness guarantee for existing users.** [Credential:33–36](../packages/db/src/models/Credential.ts#L33) adds a unique partial index without duplicate remediation or an awaited migration/index-readiness gate. Legacy duplicate TOTP records were possible under the reviewed implementation. On disposable MongoDB, installing this index over duplicate legacy rows failed with `E11000`. A clean test database cannot demonstrate upgrade safety. Supply an explicit migration/recovery policy that preserves legitimate factors and verify index installation before relying on it. Do not silently delete authenticators. Test an upgrade fixture containing duplicates and missing replay/version fields.

4. **P2 — Refresh tokens are now erased during successful login/onboarding (new regression).** Both [login:60,79–88](../apps/web/src/app/(auth)/login/page.tsx#L60) and [onboarding:112–119](../apps/web/src/app/(auth)/onboarding/security/page.tsx#L112) install the returned refresh token, then call `saveAccount` without it. [account-store:88](../apps/web/src/lib/account-store.ts#L88) calls `setSessionTokens` again, which now removes an omitted refresh token ([session:14–17](../apps/web/src/lib/session.ts#L14)). VM execution of the real helpers confirms loss; account switching has no saved token pair to restore. Pass/store the pair on authentication and preserve it during profile-only account updates. No refresh endpoint/client refresh lifecycle exists yet.

5. **P2 — Account/redirect recovery remains inconsistent (R10).** An A request rejected after switching to B still unconditionally clears B; the VM diagnostic confirms this. Compare the request's original session with the active one and invalidate only the affected saved credentials. The new `/login?reauth=1` cookie-clearing branch works only when callers use that flag ([middleware:28–31](../apps/web/src/middleware.ts#L28)); [server checkAuth:71](../apps/web/src/server/middleware/checkAuth.ts#L71) still redirects failures to plain `/login`, and account/tenant 403s still bypass browser cleanup. Thus stale-cookie redirects and suspended-account recovery are not fully corrected. Test direct server navigation and delayed responses across an account switch; browser end-to-end behavior remains unverified.

6. **P2 — Genuine WebAuthn onboarding is not connected.** [login:18–23](../apps/api-server/src/functions/auth/login/run.ts#L18) creates only TOTP onboarding state. No reachable caller generates a `FIRST_LOGIN_ONBOARDING` passkey challenge. Registration options create `PASSKEY_REG` tickets and require active-user authentication; onboarding completion requires the different purpose and throws “No passkey challenge issued” ([AuthService:449](../packages/service/src/services/AuthService.ts#L449)). A diagnostic using the real login handler/challenge storage reproduced that rejection. The positive WebAuthn branch does not prove a usable ceremony. Either explicitly document temporary TOTP-only onboarding, consistent with the original review's safe fallback, or connect and test a genuine onboarding ceremony. Do not label it verified.

7. **P2 — Finish isolation and socket lifecycle verification (R8/R6).** Require an explicit disposable connection, unique per-run database identity, and cleanup tied to that identity/ownership; fail closed before touching an inherited application connection. Add a server expiry/revalidation mechanism for inactive sockets, and register/clean up listeners safely if the peer closes during async authentication. The dispatch fixes are useful, but the report supplies no real socket tests for expiry, tenant suspension, revocation, reauthentication, or database failure.

**Additional changed configuration contract:** [connection:21–32](../packages/db/src/connection.ts#L21) now gives a URI's database path precedence over `MONGODB_DB_NAME`; the baseline used the environment database name unless an explicit option overrode it. Deployments where those settings differ will select a different database after this change. This is confirmed by source comparison; no deployment was inspected. Preserve the prior contract or provide an explicit migration/configuration change.
